RealSense on the tool flange

the pilot's seat — see what the robot sees, then send it there
✦

An Intel RealSense D435 rides on a printed bracket on the wrist of a Universal Robots arm (a UR3e and a UR20 in this cell). A laptop is the brain for now: it streams colour + depth from the camera, lets a person click an object, turns that click into a point in the robot's base frame, and asks the controller to move the tool to it — through one safety-checked, audited path. The same laptop exposes the whole cell to an agent (Claude) over MCP, so "look, segment, locate, move" can be driven by a human in a browser or by an agent in a terminal, and every action lands in the same event log.

Demo goal: live camera on the flange, the cockpit on the laptop, a single click that lands the tool 10 cm above the object — on the simulator first, then on the real arms. Later the same stack moves onto the NVIDIA GPU inside the UR controller (UR AI Accelerator) with no code change beyond the cell profile.

Status at a glance (2026-09-12): software built and tested on the synthetic camera + a dry-run robot; D435 verified streaming on the dev Mac earlier this month; not yet run on the Windows laptop, the UR3e, or the UR20; bracket not yet printed; hand-eye transform is the bracket's nominal seed, uncalibrated. Field log at the end.

chapter 2

The pipeline, in five steps

1

Capture RGB-D

Depth and colour both at 848×480 (the D435's native stereo mode; on this camera mismatched sizes return an all-black colour image). The SDK's spatial + temporal filters run in the disparity domain before alignment, the sensor sits on the High Accuracy preset with the projector at full power (written after the first frameset — writing earlier stalls a fresh open). One thread pumps the camera; the page long-polls /api/rgbd.

2

Segment with a click or a box

A click sends a point prompt, press-drag-release sends a box. The default segmenter is pure-Python region growing by colour similarity and depth continuity (~10 ms); --segment-backend sam swaps in Segment Anything (needs the sam extra, GPU or mps). Same output shape either way.

3

Measure the object

Per segment: area, bbox, centroid, depth median, metric extent, orientation, and the 3D point in the colour-camera frame (point_m) from the colour intrinsics and the aligned depth. A grasp hint (top-down, across the minor axis) rides along for the next step.

4

Hand-eye: camera frame → flange → base

The flange pose comes live from the controller (ur_flange_pose: TCP pose, active TCP offset, and the controller's own pose_trans(tcp, pose_inv(offset)), cross-checked against the host's arithmetic). The camera-in-flange transform is the bracket's nominal seed for the print in use (PERCEPTION_BRACKET=eseries|ur20), or a real calibration via PERCEPTION_T_FLANGE_CAMERA.

p_base = T_base_flange · T_flange_depth · T_depth_color · p_color

T_base_flange    live, from the controller (get_actual_tcp_pose + get_tcp_offset)
T_flange_depth   bracket seed (eseries / ur20) or PERCEPTION_T_FLANGE_CAMERA
T_depth_color    the SDK's extrinsics, read at open (~15 mm along x on a D435)
p_color          the segment's point_m
5

Approach pose, then one movel

Locate returns the base-frame point plus an approach pose: the TCP placed standoff_m (default 0.10 m) short of the point along the camera's viewing ray, keeping the tool's current orientation. Nothing moves. Move is one absolute ur_move_tcp through the same schema-validated, safety-enveloped, audited registry the CLI and MCP use — refused when the robot isn't RUNNING, over the speed caps, or outside reach. 0.1 m/s by default.

Verified so far: steps 1–3 on the D435 (dev Mac, 2026-09-04); steps 4–5 end to end on the PolyScope X simulator 10.13.0 in Remote mode with the synthetic camera (flange readback matched the controller; Move landed on the approach pose to 0.1 mm). Not yet with the camera on the bracket or on a real arm; the sim's TCP offset is zero, so the offset half of the arithmetic is covered by unit tests only.
chapter 3

The pilot's seat

Three things, all on the laptop, all reading the same cell profile: a cockpit in the browser, a doctor in the terminal, and an MCP server that hands the whole cell to an agent.

The cockpit — perception --cell ur20 gui

Colour + Depth

Live 848×480 with hover-to-measure on the depth panel (metres under the cursor), click or drag to segment on the colour panel, near/far range with auto-fit.

Object + Robot

The segment's features; Locate in base shows every intermediate frame and the approach pose; Move TCP to approach asks for confirmation, then sends one movel.

Pilot new

Status chips (robot / safety / control / program), Bring up, STOP, Freedrive, Doctor, a base-frame jog pad (1–50 mm, one safety-checked movel per press), and the Events log.

The header chips summarise the camera (kind, USB link, fps) and the robot (mode · safety · control). Everything a button does is one call into the same tool registry an agent uses, and lands in the Events log with its outcome and any safety verdict — so a person watching the browser and an agent reading cam_events see the same history.

The doctor — perception --cell ur20 doctor

A pre-flight checklist for the four things that fail independently: the SDK, the camera, the network path, and the controller's state. Every failed check carries its fix in words. Add --stream to open the camera and judge real frames (black colour, sparse depth, fps); --json for machines. The cockpit's Doctor button runs the same report with the live stream. Sample output, exactly the shape it prints (this run: dev Mac, no camera plugged in, no robot):

Verdicts: READY (everything, including motion), STATE ONLY (motion gated) (state reads work; a Local-mode or protective-stop check failed), NOT READY. The doctor also spots a platform mismatch — cell says PolyScope X but only the e-Series Dashboard port answers — and tells you which UR_PLATFORM to set.

The keys — perception-mcp

One MCP server (stdio, stdlib JSON-RPC, zero deps) serving two tool families. The robot tools are the full urctl registry, driving the controller directly through the safety envelope + audit log. The camera and cell tools go through the running cockpit, because one process must own the USB camera and the cockpit is it. When no cockpit is up, the cam_* tools answer with an in-band error that says how to start one; the robot tools keep working.

chapter 5

Simulators

PolyScope X simulator (ursim-px)

The controller without the robot: make simx-up (Apple Silicon: HOST_ARCH=arm64 make simx-up; ROBOT_TYPE=UR20 picks the model). Web UI on http://localhost:8000 — open it in Chrome. Pinned to image 10.13.0: on 10.14 the Services toggles never stick. Published ports are offset so it can coexist with the e-Series sim: Robot-API 8000, Primary 31001, RTDE 31004 — exactly what the sim cell sets.

Two pendant steps with no network equivalent (they apply to the real robots too):
1. Remote control mode — a toggle on the Safety screen. Every mutating Robot-API call (power on, brake release, load, play) returns 403 in Local, and on PolyScope X Primary URScript is silently ignored in Local (verified 2026-09-04 on the sim). State reads work in Local.
2. Services — hamburger → Settings → Security → Services: enable Primary Client Interface and RTDE (admin password). Off by default.

UR's published default passwords (first use forces a change): admin easybot, operational mode operator.

The synthetic camera

--fake or PERCEPTION_FAKE=1 replaces the RealSense with a deterministic scene — three coloured disks on a wall at ~1.2 m, plausible D435 intrinsics, identity depth→colour extrinsics, a slow wobble so long-polls always have a new frame. The whole cockpit, the doctor's --stream check, the MCP tools and the test suite run on it with no hardware.

The sim cell ties them together

$ HOST_ARCH=arm64 make simx-up          # then in Chrome: Remote mode + Services toggles
$ uv run perception --cell sim doctor  # expect: stream ok, robot reachable, control REMOTE
$ uv run perception --cell sim gui     # synthetic camera + the sim: Bring up → jog → click → Locate → Move

Docker note for the dev Mac: the e-Series URSim image does not boot under Docker Desktop's Rosetta or QEMU emulation here, which is one reason the perception work targets PolyScope X (native arm64 image).

chapter 6

Do it yourself

Windows laptop setup

  1. Clone the repo. In PowerShell: powershell -ExecutionPolicy Bypass -File scripts\setup-windows.ps1 -Cell sim. It installs uv (winget astral-sh.uv, or the official script), downloads RealSense.SDK-WIN10-2.58.4.*.exe from the librealsense GitHub release and runs it (click through; you need the SDK, not just the Viewer), sets REALSENSE_LIB to C:\Program Files (x86)\Intel RealSense SDK 2.0\bin\x64\realsense2.dll, runs uv sync, then the doctor. not yet run on the laptop
  2. Plug the D435 into a USB 3 port with a short cable (≤ 2 m, no hub). Re-run scripts\cockpit.ps1 -Doctor -Stream: expect sdk, camera and stream to pass.
  3. Put the controller's IP into the cell file: perception\cells\ur3.env or ur20.env, UR_HOST=… (pendant: Settings → System → Network). Or export UR_HOST in the shell — the shell wins.

On the pendant (once per robot)

  • Settings → Security → Services: enable Primary Client Interface and RTDE.
  • Switch to Remote control (Safety screen on PolyScope X). Leave it there for the session; the doctor's robot.control check tells you if it slipped back.

First-run checklist

  1. scripts\cockpit.ps1 -Cell ur20 -Doctor → verdict: READY (or read the fix: lines).
  2. scripts\cockpit.ps1 -Cell ur20 -DryRun first: every button validates and audits but sends nothing. Then without -DryRun.
  3. Bring up → chips show RUNNING · NORMAL · REMOTE.
  4. Jog +Z 10 mm, then −Z: the TCP line under the pad moves by 0.010 m and the Events log shows both moves with their safety verdicts.
  5. Put an object 30–60 cm in front of the camera, click it, read point (cam) m.
  6. Locate in base: check host/controller Δ is ~0 mm and the approach pose is sane (above the object, tool orientation unchanged).
  7. Move TCP to approach: confirm. First time, from an elbow-bent pose (not fully extended — see C154A0 below), with nothing between the tool and the object.
  8. Same from Claude: cell_doctor → cam_snapshot → cam_segment → cam_locate → cam_move_to_approach, then cam_events to read back.

The bracket (hardware/d435-tool-bracket/)

Two independent prints, one per flange (parametric CadQuery; STL/STEP in out/; spec in its README). Rev B.2, not yet printed.

eseries print — UR3e (and UR5e/10e/16e)ur20 print — UR20 / UR30

These seeds come straight from the CAD (out/build_info.json; a unit test holds the code to it) and are not a calibration: a printed part will not hold ±1°, and 1° at 0.5 m is ~9 mm. A hand-eye calibration replaces the seed via PERCEPTION_T_FLANGE_CAMERA="[x, y, z, rx, ry, rz]" (depth frame in the flange frame, metres + UR rotation vector); the cockpit's hand-eye row and the doctor say which is active. The active TCP offset is read live from the controller, so tool changes need no code — but if the tool is not at the flange, author any saved programs with script nodes, not MoveJ/Waypoint nodes (PolyScope's MoveJ IK goes through the active TCP).
